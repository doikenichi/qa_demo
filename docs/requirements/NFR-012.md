## Requirement

> The engineering standards exist as executable artifacts whose own checks run in CI,
> not as prose nobody can fail.

The authoritative statement of what NFR-012 requires is in the spec at
[NFR-012 — Standards as executable artifacts](../../appointment-booking-project.md#non-functional-requirements).
This document holds the acceptance criteria, the verification plan, and the evidence links.
It restates no rule.

The artifacts are the nine skills and five review agents listed in
[Engineering standards as artifacts](../../appointment-booking-project.md#engineering-standards-as-artifacts).
That table is the authoritative set — this document does not restate the count or the names.

## Acceptance criteria

Each criterion maps to one item in the spec's four-item checklist for NFR-012.

**AC-1 (checklist item 1): Skill eval suites green; withheld-skill test deterministically fails.**  
Every skill in [Engineering standards as artifacts](../../appointment-booking-project.md#engineering-standards-as-artifacts)
has an eval suite under `.claude/evals/<skill-name>/`. The suite runs in CI and is green.

The suite loads the committed skill file itself as the model's system prompt, via the
`.claude/evals/claude-provider.mjs` provider — so deleting or weakening
`.claude/skills/<skill-name>.md` makes its suite stop passing. An eval that inlines its
own copy of the skill text measures that copy, not the artifact, and cannot satisfy this
criterion.

A separate withheld-skill configuration (the same assertions, a generic assistant system
prompt) must fail — not sometimes, always — confirming the suite is measuring the
artifact, not the model.

Each assertion targets a phrase the skill makes distinctive rather than prose the model
may reword. This is not a style preference: an assertion on ordinary phrasing goes red on
a correct answer, and NFR-001 bans the retry that would paper over it. Assertions are
chosen by repeated measurement, and a config records the candidates it rejected and the
observed rate, so a later reader can see why the current one was chosen. The provider runs
with `--safe-mode`, `--restricted` and `--tools ""` so the withheld run can neither
auto-discover the skill from the working directory nor read it off disk. `--bare` disables the
same discovery but also breaks credential loading, so it is deliberately not used — see the
header comment in `.claude/evals/claude-provider.mjs`;
`.claude/evals/verify-withheld.mjs` additionally rejects a run that merely errored, so a
quota or transport fault cannot be recorded as a successful proof.
See [NFR-001](../../appointment-booking-project.md#non-functional-requirements): retries are
banned everywhere; a withheld-skill test that only usually fails is not evidence and is
rewritten until it is.

**AC-2 (checklist item 2): Review agents run on every PR and record findings.**  
Every review agent in the same table runs on every pull request and its findings are
recorded in that pull request, including the run where it finds nothing.
`.github/workflows/review-agents.yml` drives each agent through
`anthropics/claude-code-action`; every AI step is `continue-on-error`, so no agent can pass
or fail the build.

Each finding is a single line: the file and line, what is wrong in at most 15 words, the rule
or requirement identifier in brackets, and the fix after `->` in at most 5 words. For example:
`` - `BookingService.java:88` — inline Instant.now() (NFR-001) -> inject Clock ``. The shape is
stated once, in the workflow prompt, and each agent file carries a one-line pointer to it
rather than a copy. A report that arrives in another shape is recorded as **unreadable**, not
as clean.

Each agent writes its findings to `review-findings/<agent>.md` and posts no comment. The
`post-review-summary` job collates those files into one block in the **pull request body**,
between the `<!-- review-agents:start -->` and `<!-- review-agents:end -->` markers that
`.github/pull_request_template.md` carries. Collation is
`.github/scripts/collate-review-findings.mjs`, a plain script with no AI in it, so the same
findings produce the same block byte for byte and nothing sits inside the gate that an LLM
evaluated.

Two properties of that job are what make it evidence rather than decoration, and both are
covered by `node --test .github/scripts/*.test.mjs`, which the job runs before it touches a body:

- The splice replaces only what lies between the markers, so author-written text in the
  body is never overwritten.
- An agent that produced no findings file is recorded as **did not report**, never as clean.
  A crashed agent recorded as clean would be false evidence, which is exactly what this
  acceptance criterion exists to prevent.

The expected set of agents is read from `.claude/agents/`, not from a list in the workflow
or the script, so an agent added to the
[standards-artifact table](../../appointment-booking-project.md#engineering-standards-as-artifacts)
and committed cannot be silently omitted from the summary.

A clean run is required evidence, not optional, and is only recorded here once observed on a
real pull request. **Known limitation:** a pull request from a fork receives a read-only
token, so the body cannot be edited there; the summary is then recorded in the run's step
summary and the uploaded `review-summary` artifact instead. No fork pull request is expected
in this project, which is single-author.

**AC-3 (checklist item 3): Gate fails on a planted violation of each kind.**  
The lint and scanning gate (`.github/workflows/gate.yml`) fails a pull request when it
contains a planted violation of each kind:
- Formatting breach (Spotless / Biome)
- Static-analysis finding above the configured severity (SonarCloud / CodeQL)
- Contract-lint error (Spectral on `contracts/openapi.yaml`)
- Chart-lint error (`helm lint` / chart-testing / kubeconform)
- Committed secret (gitleaks)
- Vulnerable dependency (Trivy / dependency-review)

Each proof is a **closed** pull request with its failed check visible. The planted secret is
a fabricated value that matches the scanner's pattern and authenticates to nothing — never a
real credential. None of these branches merges.

**AC-4 (checklist item 4): `docs/ai-sdlc.md` names what AI may draft and may never decide.**  
`docs/ai-sdlc.md` exists and documents, for every generated artifact class: the prompt used,
the human who reviewed it, and the decisions AI is never permitted to make. It states the
honest limitation: none of this makes a generated artifact correct; it makes the human gate
visible.

**Note on planted-violation PRs:** All six exist and all six are red on the single required
`Quality gate` check, each for its intended job. Each is a separate throwaway branch carrying
exactly one planted violation, and none is merged. **They are still open**, so AC-3 is not yet
satisfied: the criterion asks for a *closed* pull request with its failed check visible, which
is what makes the proof unmergeable evidence rather than a pending change.

Two secondary failures are the same planted violation caught twice, not extra defects:
PR #4's `SonarCloud static analysis` job runs `./gradlew build`, which depends on `check` and
so on `spotlessCheck`; PR #9's `Trivy (dependency + filesystem)` job does secret detection and
found the same fabricated `AKIA…` string gitleaks found. PR #8 additionally shows Sonar's own
`SonarCloud Code Analysis` app check failing, which is neither a required context nor part of
the gate — corroboration, not evidence.

AC-3-b needed a gate change to be provable at all: `analyze@v4` uploads SARIF and exits 0
regardless of findings. A `Fail on CodeQL findings` step was added (PR #3, `e370d5a`), and
PR #8's job record shows `Perform CodeQL analysis` succeeding and only that new step failing —
so the red is a finding, not a broken build. `sonar.qualitygate.wait=true` was deliberately
not set, because it would wire a coverage percentage into the gate, which NFR-009 forbids.

Because the six branches were cut before `e370d5a` merged, their diffs against `main` read as
*removing* that step, which is what the review agents flagged on #4, #6 and #7. The finding is
a true reading of the diff and a further reason none of these branches may be merged.

**Note on the flaky eval (AC-1):** the `code-standard` suite asserted `contains: not adopted`,
prose the model may reword. It failed on PRs #4 and #5 and passed unchanged on #6 to #9. Measured
on one commit against the committed provider, the old assertion passed 1 of 4 runs while the
model answered correctly every time; an assertion retargeted onto the requirement IDs
`NFR-002` and `NFR-004` passed 4 of 4. Per the flaky-test rule this reverts TC-NFR-012-1 to
not-done and blocks milestone exit until a fresh green run exists. The fix is `a1dc3f3` on
`fix/flaky-code-standard-eval`, awaiting merge; a same-day issue linked to NFR-012 is required
and is the human's to open. The withheld-skill proof never used the affected assertion —
`promptfooconfig-withheld.yaml` carries only the `fractional_seconds` test — so AC-1's
withheld leg is unaffected.

## Minimum-evidence floor

Taken directly from the spec (do not restate — see
[NFR-012 floor](../../appointment-booking-project.md#non-functional-requirements)):

> Every skill's eval suite green in CI with one proven to fail without its skill, and
> the lint/scan gate failing on planted violations of each kind.

This floor names runs and checks, not files. A committed eval config that has never run
is not evidence. A gate configured but never tested against a violation is not evidence.

This document is not finished until the Evidence table above has a run link in every row.
